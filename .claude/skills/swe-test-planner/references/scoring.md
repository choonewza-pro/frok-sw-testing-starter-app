# Scoring Rubrics: Impact & Likelihood

Used by `swe-test-planner` Step 3 and Step 2 respectively.

---

## Impact Score (1–5)

Impact measures **how bad it is if this feature breaks** — based on business
consequence, not technical complexity.

| Score | Label | Criteria | Examples |
|-------|-------|----------|---------|
| 5 | Critical | Data loss, financial loss, security breach, complete system failure | payment, billing, checkout, auth, login, permission, role, data deletion |
| 4 | High | Core user journey broken, significant data corruption, compliance risk | order, cart, inventory, booking, user registration, file upload |
| 3 | Medium | Important feature degraded but workaround exists | search, notification, profile, report, export, dashboard |
| 2 | Low | Minor inconvenience, cosmetic issue with minor functional impact | pagination, sorting, filter, date picker, tooltip |
| 1 | Negligible | Pure cosmetic, no functional or data impact | theme, color, layout, animation, static text, icon |

### Keyword Heuristics (auto-assign Impact)

Scan module/file/route names for these keywords (case-insensitive):

**Impact 5:**
```
payment, pay, billing, bill, invoice, checkout, transaction, charge,
auth, login, logout, signin, signup, password, token, permission,
role, access, rbac, acl, secret, encrypt, delete, purge, destroy
```

**Impact 4:**
```
order, cart, basket, inventory, stock, booking, reservation,
register, onboard, upload, import, export-critical, kyc, verify
```

**Impact 3:**
```
search, filter, report, dashboard, notification, alert, email, sms,
profile, account, setting, preference, export, download, print
```

**Impact 2:**
```
list, table, paginate, sort, date, picker, tooltip, modal, drawer,
sidebar, breadcrumb, tab, accordion
```

**Impact 1:**
```
theme, color, style, css, layout, animation, icon, logo, banner,
static, landing, about, faq, help
```

If a module matches multiple levels, take the **highest** match.
If no keyword matches, default to Impact **3** and note it as "unclassified."

## Likelihood Score (1–5)

Likelihood measures **how probable it is that a bug exists** — based on change
frequency and complexity signals.

### Primary: Git Commit Frequency (last 90 days)

Run:
```bash
git log --since="90 days ago" --pretty=format: --name-only | sort | uniq -c | sort -rn
```

Map total commits touching the feature's files:

| Commits (90d) | Score | Label |
|---------------|-------|-------|
| ≥ 15 | 5 | Very High — frequent changes, high chatter |
| 10–14 | 4 | High — actively developed |
| 5–9 | 3 | Medium — occasional changes |
| 2–4 | 2 | Low — stable, rarely touched |
| 0–1 | 1 | Very Low — untouched or legacy |

### Secondary: File-Pattern Modifiers

Apply **+1** (max 5) if any of these are true for the feature:

| Signal | Rationale |
|--------|-----------|
| Calls external API / third-party SDK | Integration points break silently |
| Contains async / queue / job / cron logic | Timing bugs are hard to catch |
| Has complex conditional branches (≥ 3 nested ifs) | Cyclomatic complexity |
| Recently had a bug fix commit (keyword: `fix`, `hotfix`, `patch`) | Bug-prone area |
| Is new (< 30 days old, no existing test files) | Untested new code |

Apply **−1** (min 1) if:

| Signal | Rationale |
|--------|-----------|
| Has existing test coverage (test file found) | Already partially validated |
| Module is autogenerated / scaffolded | Low manual logic risk |

### Fallback (no git)

If git is unavailable, use file-pattern modifiers only and default Likelihood to **3**.
State clearly in output: `⚠️ Git unavailable — Likelihood based on heuristics only`.

---

## Likelihood Calculation Walkthrough

Likelihood is calculated in **two phases** — Base Score first, then Modifiers.
They are **independent** and combine additively (capped at 5, floored at 1).

```
Final Likelihood = clamp(Base Score + Modifiers, min=1, max=5)
```

### Example: Payment feature

| Step | Signal | Value |
|------|--------|-------|
| Base | 18 commits in 90 days → "≥ 15" bucket | +5 |
| Modifier | External API (Stripe SDK found in files) | +1 |
| Modifier | Async logic (`async/await`, webhook handler) | +1 |
| Modifier | Recent bug fix commit (`fix: payment retry`) | +1 |
| Modifier | Has existing test file (`payment.test.ts`) | −1 |
| **Final** | clamp(5 + 1 + 1 + 1 − 1, 1, 5) = clamp(7, 1, 5) | **5** |

### Example: Landing Page feature

| Step | Signal | Value |
|------|--------|-------|
| Base | 0 commits in 90 days → "0–1" bucket | +1 |
| Modifier | No external API, no async, no bug fixes | +0 |
| Modifier | No test file (but Impact=1, so irrelevant anyway) | +0 |
| **Final** | clamp(1 + 0, 1, 5) = 1 | **1** |

### Example: New feature (no git history yet)

| Step | Signal | Value |
|------|--------|-------|
| Base | 0 commits (added yesterday, shallow history) | +1 |
| Modifier | New file < 30 days, no test file | +1 |
| Modifier | Calls external API | +1 |
| **Final** | clamp(1 + 1 + 1, 1, 5) = **3** | **3** |

> **Key rule:** Base Score and Modifiers are always computed separately.
> Never skip the Base Score even if Modifiers alone would reach 5.
> Always show the breakdown in the scan summary for traceability.
